# Conversation Graph 逻辑设计（定稿）

本文是 Conversation Graph 的**设计基准**。正文描述图应当是什么样，不描述代码现在是什么样；两者不一致时，以本文为准，由代码来对齐。

- 视觉定稿来源：Claude Design 项目 `Conversation Graph.dc.html` turn 4（`4a`–`4d` 四种关系各一张，`4f` 同框，`4g` 点开态）。

---

## 0. 设计立场

三句话概括这套图要坚持的东西：

1. **图上只有四种关系**——接续、分叉、fork、merge。没有第五种，新需求要么归进这四种，要么先改这份文档。
2. **上下文不成线。** 一个 PA 带了哪些 PA，是一次请求的成分清单，不是节点之间的长期关系。画成线会和血缘线抢同一套语义，所以它只在点开时用"其余变淡"表达。（merge 线看似反例，其实不是：它连的确实是来源，但那是**建立那一刻被写死、之后不再变的**上下文——冻成了血缘，才有资格成线。）
3. **形状只从账本字段推出来。** 渲染层不做任何补全、不猜测缺失的边；数据说不清的关系，就不画。

## 1. 一个 PA 携带的全部信息

一个完成的「提问 + 回答」回合是一个 `PA` 节点，不可原地改写。图上的一切形状都只由这五项决定，多一项都没有：

| 概念 | 回答的问题 | 图上的体现 |
| --- | --- | --- |
| **归属 Session** | 「我属于哪条对话」 | 不直接成形；决定一次选择是 Fork 还是 Merge（§5） |
| **主线父节点** | 「我接着谁往下走」 | 列的继承、主干高亮 |
| **全部父节点** | 「谁指向我」 | 入线的条数与形态（§2） |
| **上下文清单** | 「我这一轮实际带了哪些 PA，按什么顺序」 | 只在点开时用变淡表达，**不成线**（§3） |
| **fork 来源** | 「我是不是某个 PA 的副本」 | 有值即副本：不占编号、不占时间轴、无血缘入线（§2.2） |

「主线父节点」和「全部父节点」必须分开，因为它们回答的是两个问题：前者决定**版面**（这个节点站在哪一列、主干怎么走），后者决定**关系**（画几条入线）。一个 merge 节点有多个父节点，但它仍然只能站在一列上。

## 2. 四种关系

图上只有两种线：**黑色血缘线**和**淡紫 merge 线**。外加 fork 用的一根**双向箭头**——它不是线，是「这两个是同一个 PA」的等号。

| 关系 | 判定 | 画法 |
| --- | --- | --- |
| **接续** | 单父，且这个父节点只有我这一个子节点 | 一条直竖线，子节点继承父列 |
| **分叉** | 单父，但这个父节点已经有子节点了 | 子节点换到右边新列，线走「下 → 横 → 下」 |
| **fork** | 我是某个 PA 的副本 | 副本紧挨原 PA 右边一格，中间一根双向箭头；**副本没有血缘入线** |
| **merge** | 多父 | 每个来源一条淡紫线，汇到同一根横向母线，落进 merge 节点顶部 |

判定按这个顺序落地：先看是不是副本，再看父节点有几个，最后才看那个父节点有没有别的孩子。四种情况互斥且穷尽。

### 2.1 接续与分叉是同一个公式

不是两条规则，是同一个公式的两种结果。血缘线永远是：

```
M 父中心x 父底y  V 中点y  H 子中心x  V 子顶y
```

同列时父子中心重合，肘形自动退化成一条直竖线。横段永远落在两行正中间（父底 + 29px），因此不可能穿过任何节点。

列的分配规则：

```
根节点             → 开一列
第一个子节点       → 继承父节点的列
第二个及以后子节点 → 各开一列（往右）
```

「第一个」按创建时间算，不按视觉位置。这条保证了**已有的节点不会因为后来长出新分支而挪窝**：今天 PA2 独占 PA1 的列走一条直线，明天 PA5 也接到 PA1 上，动的只有 PA5。行号同样是创建顺序，同刻则以 id 破平局。

### 2.2 fork：副本是等号，不是子节点

Harness 官方 fork 会复制一段连续的历史前缀。被复制的末端 PA 在图上显示为一个**副本节点**：

- 副本与原 PA **同行**，排在原 PA 右侧第一个空位；两者之间一根 1.1px 双向箭头，箭头头 4px。
- 副本**不占 PA 编号**，也**不占时间轴格子**。标签是原 PA 编号 + 一个 10px 等宽 `FORK` 徽标（写法同 `HEAD`）。
- **副本没有自己的血缘入线。** 箭头已经说明「这两个是同一个 PA」，再从原 PA 的父节点拉一条线过来，就是同一件事说两遍。
- 副本向上只靠这根箭头，向下正常长子节点——fork 之后第一个真正新增的 PA 从副本继续延伸。

**副本不强占列，分叉优先。** 原 PA 右边第一格永远先给分叉子节点；副本往右挪到第一个空位，**双向箭头随之拉长**。这条优先级和先后顺序无关：即使副本先画出来，后来才长出分叉子节点，让位的仍然是副本。

理由是两者的代价不对称。箭头本来就是可伸缩的，拉长不损失任何含义——只要它是水平的、双向的、两端是同一个编号，再长也读作等号。而分叉子节点一旦挪动，会带着它整条后续谱系一起挪。

### 2.3 merge：来源并列出发，汇到一根母线

- 每个来源从自己的底边垂下一条 1px 淡紫线，汇到同一根横向母线，再一起落进 merge 节点顶部；母线落在两行正中间。
- 来源如果同时还有自己的子节点，两条线从同一条底边**并列出发**：黑色血缘线走节点中心，紫线偏右 8px。
- merge 节点带一个 10px 等宽 `MERGE·n` 徽标，`n` 是**去重后**的来源数。

**入线一律全紫，没有例外。** merge 节点在数据上仍有一个主线父节点（它决定这个节点站在哪一列），但那只是版面语义，不再对应一条黑线。理由是 merge 的产品含义就是「这几个来源平等地凑成了一段新历史」——Tray 里它们本来就是一排可拖动的 chip，没有谁天生是主的。所以规则收成一句：**多父节点的入线全部是紫的。**

**但要标出 latest 来源。** 全紫抹掉了主次，而「每条被并进来的谱系，是在哪里被接住的」这件事仍然需要看得见。标记用一个 10px 等宽 `LATEST` 徽标（写法同 `HEAD` / `FORK`），加在来源节点上，**常驻**——不依赖点开，静态图上一直可读。用徽标而不是变线宽或变色，是为了不给淡紫再增加第二种含义。

标在谁身上，只有一条规则：

> **每个来源 branch，取它在 Tray 顺序里最后出现的那个节点。**

- 来源跨了多个 branch → 每个 branch 各出一个 `LATEST`，标出这条谱系被并进来的断点。
- 来源全部来自同一个 branch → 规则退化，只剩一个 `LATEST`，就是 Tray 顺序的最后一个。

和 §2.1 一样，这里不是两条规则，是同一条规则的两种结果。注意判据是 **Tray 顺序**而不是完成时间：Tray 的顺序是用户拖出来的，它才是新历史里各段的真实先后，最后一格就是新提问紧接着往下说的地方。

淡紫色只用于 merge，不复用在任何其他关系上。

## 3. 点开一个节点

点开 = 只读地检查这个 PA 带了什么。**不改上下文、不切会话、不动 HEAD。**

图上的表达只有一种：

- 该节点上下文清单里的 PA 保持原色；
- 其余节点**整体降到 24% 透明**；
- **所有连线一并降到 24%**——血缘线和 merge 线都不例外；
- fork 的双向箭头**跟着它两端那对节点走**：两端亮则亮，两端淡则淡；
- 被点开的节点换一个底色（浅 `#f4f5f9` / 暗 `#26262b`）；
- **不出现任何虚线、序号或额外连线。**

**点开态不表达结构，只表达关联。** 它只回答一个问题：这个 PA 和哪些 PA 相关联。连线描述的是「谁生了谁、谁并了谁」，那是静态图的职责，点开态不重复说一遍——所以连线一起淡下去，包括亮着的那批节点彼此之间的线。结果是点开态干净到只剩一件事：**亮起来的那组节点，就是答案。**

双向箭头是唯一留下的线，因为它根本不是关系线：它说的是「这两个是同一个 PA」，属于身份而非结构，而身份正是关联性本身。它也不需要单独的规则——跟着两端那对节点走就够了。定稿 `4g` 里 PA3 那根箭头是淡的，正是因为 PA3 和它的副本都不在 PA8 的上下文里。

### 3.1 被点开的节点是什么身份，亮起来的就是什么

| 被点开的是 | 亮起来的是 |
| --- | --- |
| **常规 PA**（接续或分叉） | 它上下文清单里的那批 PA，没有别的 |
| **fork 副本**（或它的原 PA） | 两者同时保持原色，中间那根**双向箭头保留**——它就是这个节点身份的全部内容 |
| **merge 节点** | 它的来源，其中**每个来源 branch 在 Tray 顺序里最后出现的那个节点**由常驻 `LATEST` 标出；来源全在同一 branch 时，就是 Tray 顺序的最后一个 |

merge 那一行说的是**节点**，不是徽标。`LATEST` 是常驻的（§2.3），静态图上就一直在；点开 merge 时它不需要被"打开"，只是恰好落在同一批节点上。

这样表达的收益是：**亮起来的集合就是答案**。定稿 `4g` 里 PA8 点开后 PA1 PA2 PA4 PA7 亮、PA5 不亮，一眼说明 Context Tray 挑的是**单个 PA**，而不是整条祖先链——这正是本产品与"自动带上全部历史"的区别。

代价是上下文的**顺序**在图上看不出来（清单是有序的，图只给集合）。这是有意的：顺序属于 Context Tray 和详情面板，图不做第二套表达。同理，结构属于静态图，点开态也不做第二套表达。

**点开一个 fork 副本，等于点开原 PA。** 副本没有自己的上下文身份，所以两者的表现完全一致：亮起来的是同一批 PA，能做的操作也是同一套，副本和原 PA 两个节点同时保持原色——它们之间那根箭头因此也自然是亮的，不需要为它单独立规则。这是 §7 不变量 2「副本不产生新的 PA 身份」在交互层的直接结果：如果点开副本能看到不一样的东西，它就有了自己的身份。

`HEAD`、点开预览、选择这三种状态互相独立：点节点不改变选择，勾选不移动 HEAD。

## 4. 编号规则

| 对象 | 规则 |
| --- | --- |
| PA 编号 | 按创建顺序（项目图按 PA 完成时间）从 1 递增；副本不参与计数 |
| fork 副本 | 沿用原 PA 的编号 + `FORK` 徽标 |
| `MERGE·n` | `n` = 去重后的来源数。两个来源如果指向同一个 PA 身份（例如其中一个是另一个的副本），只算一个 |
| 时间轴 | 只排真正的 PA，副本不占格 |

编号是**身份**，不是位置。这就是副本不占编号的理由：它没有新的身份可编。

## 5. Fork 还是 Merge：由选择跨不跨 Session 决定

Context Tray 主操作按钮的名字随选择变化，判据只有一条：

- 选择全部来自**同一个 Session** → 把那条对话裁剪/重排后接着走 → **Fork**；
- 选择跨了**两个及以上 Session** → 新 Chat 把这些谱系接到一起 → **Merge**。

绿色候选 PA（尚未加入的预览项）计入判据，所以按钮名反映的是「按下去会变成什么」。选中的 PA 若缺少直接前驱，只发警告，**不自动补进请求**——补不补是用户的决定。

节点是可读的文本块，不是 chip：重色只出现在 2px 的左竖线上，盒子本身在静止状态下就要认得出标签。

## 7. 不变量

1. 一个 PA 一旦写入就不被改写；重组历史是**新建 Session**，不是修改旧的。
2. 副本不产生新的 PA 身份：编号、时间轴、上下文清单里都不出现它自己。
3. 上下文清单只记录**实际发出去的**那批 PA 及顺序，不做祖先补全。
4. 已经画出来的 PA 不因为后来的新增而挪位（§2.1）。**副本是唯一的例外**：它会为新出现的分叉子节点让路（§2.2）。它没有独立身份，挪动不牵连任何谱系——这也正是它可以被挪的理由。
5. 数据说不清的关系不画，但节点本身永远保留在图上——宁可孤立，不可消失。

## 8. 待定

1. **一个 merge 到底有几条紫线？** §2.3 现在写的是「每个来源一条」：Tray 里选了 5 个 PA、来自 2 个 branch，就是 5 条紫线，其中 2 个来源带 `LATEST`。另一种收法是每个 branch 只连它的 Tray 末位节点，即 2 条紫线、紫线与 `LATEST` 一一对应，其余 3 个 PA 只作为上下文存在、不成边。后者画面干净得多，前者胜在每个被并进来的 PA 都在图上有交代。这条会直接改变 `MERGE·n` 里 `n` 的含义（来源数 vs branch 数）。
2. **`4g` 需要重画一版。** 那张图目前画的是连线保持原色、只有 fork 箭头变淡；§3 已定为连线一并变淡。以文字为准，图跟着更新。
3. **`LATEST` 徽标尚未出现在任何一张定稿图里。** `4d` `4f` 的 merge 场景需要补画两种：来源跨 branch 时每条谱系各带一个 `LATEST`，以及来源同 branch 时只有一个的样子。
4. **多个 `LATEST` 同框时的密度还没验证过。** 来源 branch 一多，`LATEST` 就会成排出现；它们和 `MERGE·n` 同屏是否还读得清，要画出来才知道。

   这条**依赖第 1 条**：若 merge 只连每个 branch 的 Tray 末位节点，紫线端点即 LATEST，两者一一对应，徽标可以整个取消，密度问题自动消失；只有在「每个来源一条紫线」的方案下，徽标才是必需的。

   候选解法是**给每次 merge 一个自己的颜色**。它真正要对付的是一个更窄的场景：同一个节点同时是两个 merge 的末位来源，身上挂着两条通向不同 merge 的紫线，一个徽标说不清属于谁。若采用，建议两条约束——**只染线不染节点**（节点左竖线是 PA 自己的身份，merge 是发生在它身上的事，不该改写身份色）；**色相限制在同一紫色家族内**（保住"有色 = merge"这层分类读法，色相只区分实例）。代价是家族内可区分色相约 4–6 个即到顶，且色相对色觉障碍用户几乎无效，所以颜色只能是辅助线索，文字标记必须保留。

   前置问题：**颜色通道只有一条，要先决定归谁。** branch 身份是常驻的、每个节点都有；merge 实例是稀疏的、只有几条线。若将来要用颜色区分「这个 PA 属于哪条 branch」，两套色彩系统会在同一张图上打架。
